# JsonRPC

既然我们聊到了 MCP（模型上下文协议）底层的 **JSON-RPC 2.0**，那就不得不提 **RPC（Remote Procedure Call，远程过程调用）** 了。

如果说 **REST API 路由** 是让客户端像“浏览网页、提交表单”**一样去和后端交互；那么 \**RPC 路由\** 则是让客户端像**“调用本地自己写的函数”一样，去触发远端服务器的代码。

我们同样用大白话和对比，来把“RPC 路由”这个概念彻底剥茧抽丝。

### 一、 什么是 RPC（远程过程调用）？

在传统的本地开发中，你调用一个函数长这样：

Python

```
result = calculate_tax(1000)  # 函数就在你眼前的代码里，直接运行
```

但是，如果你的算税逻辑非常复杂，必须放在一台专门的、算力很强的“算税服务器”上运行呢？你就需要跨越网络去调用它。

**RPC 的核心思想就是：把网络通信的细节全部隐藏起来。** 让客户端程序员在写代码时，感觉就像在调用本地函数一样，但实际上这个函数是在远端的另一台服务器上执行的。

### 二、 什么是 RPC 路由？

在 REST API（如 FastAPI）中，路由是靠 **URL 路径**（`/api/v1/user`）和 **HTTP 动词**（`POST/GET`）来分发的。![image-20260605105513568](/typora-user-images/image-20260605105513568.png)

而在 RPC 的世界里，根本没有那么复杂的 URL 路径，通常**只有一个统一的入口（Endpoint）**。

RPC 路由的本质，是靠请求体里携带的“函数名字（Method Name）”来决定把任务分发给谁的。

#### 一个 JSON-RPC 路由的真实结构

MCP 协议底层用的就是 JSON-RPC 2.0，当大模型想要调用一个工具时，它发出的 RPC 请求路由看起来是这样的：

JSON

```
{
  "jsonrpc": "2.0",
  "method": "tools/call",           // <-- 这就是 RPC 的“路由依据”（函数名）
  "params": {
    "name": "calculate_tax",        // 具体的工具路由名
    "arguments": { "amount": 1000 } // 传给函数的参数
  },
  "id": 1
}
```

**RPC 路由的运转逻辑：**

1. 所有的请求，不管是要查数据、算数字、还是删文件，全都发送到同一个网络地址（比如 `ws://localhost:8080/rpc`）。
2. RPC 服务端程序收到这个 JSON 后，拿眼一瞧：`"method": "tools/call"`。
3. 服务端内部的 **RPC 路由映射表** 立即启动：“哦，这个 method 对应的是我本地的 `execute_tool_function()` 这个函数，把 `params` 给它传过去！”

### 三、 RPC 路由 vs REST API 路由（FastAPI）

为了让你更直观地看出它们的区别，我们把两者放在一起对比：

| **维度**         | **REST API 路由 (FastAPI 风格)**                             | **RPC 路由 (MCP / gRPC / JSON-RPC)**                         |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **核心世界观**   | **以“资源 (Resource)”为中心**。世界是由“用户、日志、订单”等资源组成的。 | **以“动作 (Action)”为中心**。世界是由一个个“函数、方法、过程”组成的。 |
| **路由长什么样** | `POST /users` `GET /logs/2026-06-02`                         | 统一入口，内部指定： `method: "createUser"` `method: "getLogs"` |
| **URL 的数量**   | 很多。每一个不同的业务逻辑都有一个独立的 URL 路径。          | 极少。通常**只有一个 URL**（甚至没有 URL，直接走标准输入输出 Stdio 流）。 |
| **传输效率**     | 相对较慢。因为 HTTP 头部带有大量的文本信息（Header、Cookie等）。 | **极快**。因为结构极其简单，有些（如 gRPC）甚至会压缩成密不可分的二进制数据流。 |

### 四、 为什么 AI 和 Agent 框架（如 MCP）更偏爱 RPC 路由？

你可能会问，既然 FastAPI 的 REST API 路由那么流行，为什么 MCP 不用，偏偏要用 RPC 路由呢？

1. **大模型天生就是“函数调用者”：**

   大模型（LLM）天然具备的能力叫做 **Function Calling（函数调用）**。大模型思考完后，它脑子里想的是：“我要调用 `search_database(query='AI')` 这个**函数**”，而不是“我要去访问 `/api/v1/search` 这个 **URL**”。RPC 的“函数映射”完美契合大模型的思维方式。

2. **轻量与双向通信（WebSocket / Stdio）：**

   Agent 和大模型交互时，不仅客户端要给 Agent 发消息，Agent 运行过程中也要频繁、快速地向大模型、向各种外部工具要数据。RPC 配合 WebSocket 或标准输入输出（Stdio），可以实现**极低延迟的双向对话**。如果每次交互都去过一遍复杂的 HTTP REST 路由，黄花菜都凉了。

### 总结

- **REST API 路由：** 通过不同的 **URL 网址** 找到对应的后端代码（适合前后端分离的 Web 应用）。
- **RPC 路由：** 通过传递 **“方法名字符串”** 找到对应的后端代码（适合 AI 框架、微服务之间的高性能通信）。

在 MCP 中，它把 Tools、Resources 全部包装成了 RPC 的 `method`，大模型只要喊出名字，RPC 路由就会在后台帮它精准匹配到对应的 Python/TypeScript 函数去执行。
