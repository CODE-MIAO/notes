因为你在开发基于 **MITK** 的专业医疗工作站，我们需要用极其严谨的**医疗工程落地标准**来审视 MedGemma 的真实能力和输入规范。

简单来说：**MedGemma 1.5 确实是谷歌专门为了分析这类 CT/MRI 图像而训练的，但他并不擅长像 3D U-Net 那样去帮你数像素或做精准测量，他最擅长的是“像放射科高年资医生一样，结合影像表现与临床病史进行文本级的逻辑推理与诊断描述”。**

要让他发挥出最佳性能，你绝对不能只扔给他一整张带有主程序 UI、菜单栏的软件截图。在你的 MITK 后端，你应该为他定制一套标准的“图文多模态复合网关报文”。

以下是工业级集成的标准输入设计指南：

## 一、 他的输入应该是什么？（数据组装标准）

在你的独立程序后端，当医生点击“AI 协同诊断”时，你的 Python/C++ 核心代码应该把输入打包成 **【1. 脱敏结构化文本上下文】+【2. 多多模态核心关键帧图像】** 的复合结构发送给本地模型 API。

### 1. 文本层面：必须喂入“临床上下文”

医疗影像绝对不是孤立存在的。同样的 CT 表现，结合不同的病史，结论可能完全相反（比如感染 vs 肿瘤）。你必须通过 MITK 的病历管理模块打捞出以下脱敏信息：

- **患者基本体征：** 年龄、性别、主诉（如：右腰部间歇性胀痛 2 个月）。
- **影像检查元数据（来自 DICOM Header）：** 检查部位（腹部 CT）、扫描期相（如：动脉期/Arterial Phase）、层厚（如：1.5 mm）。
- **定量测量反馈（来自你 MITK 内部的算法）：** 比如你的底层算法测出了结节的 CT 值（HU）、大小，一定要作为文本喂给他。（例如：*“经后台算法测得，当前十字交叉线中心区域低密度占位大小约 $14 \times 12\,\text{mm}$，平均 CT 值约 $18\,\text{HU}$”*）。

### 2. 图像层面：不能截图 UI，要提取“纯净影像矩阵”

大模型的视觉多模态接口处理的是标准的色彩图像（如 PNG/JPG）。你的 MITK 渲染引擎应该在后台执行以下动作，而不是直接把整个软件窗口截屏：

- **应用医学窗宽窗位（Windowing）：** 根据当前的检查部位（腹部软组织窗：窗宽 $W=300 \sim 400$，窗位 $L=30 \sim 50$），把原始 16-bit 的 DICOM 灰度矩阵，线性映射成一张高清晰度的 8-bit **纯净单窗影像图片**。
- **多视图联合（Multi-view Combination）：** 顺着你目前 MITK 的三视图管线，把当前十字线对焦位置的 **横断面 (Axial)、冠状面 (Coronal)、矢状面 (Sagittal)** 这三张纯影像切片单独导出。
- **时空采样：** 由于 MedGemma 1.5 支持 3D 连续体积理解，你还可以顺着轴位（Axial），把焦点层**向前走 2 层、向后走 2 层**的切片一起导出，组成一个包含 5~7 张图的“图像序列数组”。

## 二、 实际工程请求报文（API Payload 范例）

当你在后台使用 LM Studio 或 vLLM 载入 MedGemma 后，你的 Agent 核心向其发起的 POST 请求结构应该长这样：

JSON

```
{
  "model": "medgemma-1.5-4b-it",
  "messages": [
    {
      "role": "system",
      "content": "You are an expert radiologist. Analyze the provided clinical metadata and CT image slices to provide professional findings and diagnostic suggestions."
    },
    {
      "role": "user",
      "content": [
        {
          "type": "text",
          "text": "【Patient Clinical Context】\n- Age: 56 | Gender: Male\n- Scan Type: Abdominal CT Enhanced (Arterial Phase)\n- Slice Thickness: 1.5 mm\n- Quantitative Data from MITK segmentation tool: A low-density lesion is detected at the right kidney, size ~14mm, average CT value ~18 HU.\n\n【Task】\nAnalyze the attached multi-view slices (Axial, Coronal, Sagittal) around the lesion center. Describe the lesion characteristics (e.g., enhancement pattern, borders) and give a preliminary diagnostic suggestion."
        },
        {"type": "image_url", "image_url": {"url": "data:image/png;base64,BASE64_OF_CLEAN_AXIAL_SLICE..."}},
        {"type": "image_url", "image_url": {"url": "data:image/png;base64,BASE64_OF_CLEAN_CORONAL_SLICE..."}},
        {"type": "image_url", "image_url": {"url": "data:image/png;base64,BASE64_OF_CLEAN_SAGITTAL_SLICE..."}}
      ]
    }
  ]
}
```

*(注：鉴于你在上一步测试中发现他听不懂中文指令，强烈建议在给 MedGemma 的 Prompt 里使用**全英文**进行核心影像分析任务。当他吐出专业的英文医学描述后，你在独立程序内部用 Qwen 或者常规翻译中间件将其一键转化为完美的中文放射科报告报告呈现给医生。)*

## 三、 他擅长和不擅长什么的“红线警告”

在把它封装进你的 MITK 工作站时，必须在产品和算法边界上做好分工：

### 👍 他非常擅长：

- **模式识别与经验诊断：** 比如他看过了几万例肾囊肿和肾癌的增强 CT 数据，他能根据图像里肿块的边缘是否光滑、有没有明显的动脉期不均匀强化，结合你给的 18 HU（提示偏囊性成分），在文本里分析出“这更符合良性囊肿或复杂囊肿的表现”。
- **放射学语言组织：** 他能瞬间写出一大段极其符合放射科医生书写规范的英文描述草稿，省去了医生人肉打字的时间。

### 👎 他绝对不擅长（严禁让他干的活）：

- **找细小病灶的坐标：** 你不能让他去满图找一个 2 毫米的微小结节并返回像素坐标，他经常会看漏或者瞎指（幻觉）。
- **精确的几何学测量：** 计算体积、测量最大长径、勾勒三维不规则边缘。这种高精度的物理数学计算，是你的 **MITK/ITK 传统图像处理算法以及 nnU-Net** 的绝对强项。

### 💡 工业界完美的合体落地工作流：

1. 医生在你的 MITK 界面上，用鼠标点击或者用你的分割算法勾勒出了一个疑似病灶区域。
2. 你的 C++ 代码计算出该病灶的体积、中心三维坐标。
3. 你的程序自动在后台以这个三维坐标为中心，切出 Axial/Coronal/Sagittal 三张应用了标准软组织窗的**干净图片**，自动脱敏提取病历。
4. 打包发送给后台的 MedGemma。
5. 软件界面的右侧 AI 助手面板，瞬间流式输出针对该点击区域的专家级影像解读初稿。医生在此基础上微调改动，一键提交报告。
