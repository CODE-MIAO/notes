**SSE** 的全称是 **Server-Sent Events**（服务器发送事件）。

如果说传统的 HTTP 请求是“**一问一答**”（你问一句，服务器答一句），那么 SSE 就是“**一问多答**”（你问一句，服务器像流水线一样不停地给你发消息，直到发完为止）。

它是实现 AI “打字机”效果的核心技术。

---

### 1. 形象理解 SSE
想象你在一家拉面馆：
*   **普通 HTTP (非流式)**：你点完面，坐在座位上等。厨师在后面拉面、煮面、放调料。过了 5 分钟，厨师把一整碗热腾腾的面端到你面前。
*   **SSE (流式)**：你点完面，厨师开始拉面。每拉出一根，他就从厨房窗户扔给你一根；每下一根面，他又扔给你一根；最后再把汤勺过来。你一边接，一边就能开始吃了。

### 2. SSE 的工作原理
1.  **客户端发起请求**：浏览器或程序发个请求说：“我要听听 AI 怎么说，请开启 SSE 模式。”（通常在 Header 里设置 `Accept: text/event-stream`）。
2.  **服务器保持连接**：服务器不立刻切断连接，而是维持这个 HTTP 通道。
3.  **持续推送数据**：服务器把内容拆成碎片，按照特定格式一条条发出去：
    *   `data: 结果1`
    *   `data: 结果2`
    *   `data: [DONE]` (表示发完了)

---

### 3. SSE 的特点

*   **单向通信**：只有服务器往客户端发，客户端不能在同一个连接里回话。这非常适合 AI：因为 AI 回答通常很长，而你的问题很短。
*   **基于标准 HTTP**：它不需要像 WebSocket 那样建立特殊的协议，只要普通的 Web 服务器都能支持。
*   **自动重连**：如果网络断了一秒，SSE 协议会自动尝试重新连接，并尝试从断掉的地方继续接收。
*   **轻量级**：它传的是纯文本，开销非常小。

---

### 4. 为什么 AI 偏爱 SSE 而不是 WebSocket？
你可能听过 **WebSocket**（也是实时通信技术）。但 AI 厂商（OpenAI, DeepSeek）几乎都选了 SSE，原因如下：

| 特性       | SSE (AI 常用)                   | WebSocket                   |
| :--------- | :------------------------------ | :-------------------------- |
| **方向**   | 单向 (服务器 -> 客户端)         | 双向 (互相发)               |
| **复杂度** | 非常简单                        | 较复杂                      |
| **防火墙** | 友好 (就是普通的 HTTP)          | 较难 (有些公司防火墙会拦截) |
| **场景**   | **AI 回复、股价看板、新闻滚动** | **网络游戏、实时聊天室**    |

**结论**：AI 回答问题时，你不需要在它说话的时候打断它（单向就够了），所以 SSE 是性价比最高的选择。

---

### 5. SSE 的报文长什么样？
当你开启 `stream: true`，你会看到控制台里的数据长这样：

```text
event: message
data: {"choices":[{"delta":{"content":"医"}}]}

event: message
data: {"choices":[{"delta":{"content":"学"}}]}

event: message
data: {"choices":[{"delta":{"content":"影"}}]}

event: message
data: {"choices":[{"delta":{"content":"像"}}]}

data: [DONE]
```

**程序逻辑**：你的前端代码会有一个“监听器”，每当收到一个 `data:`，就把它里面的 `content` 拿出来，贴到屏幕上。这样用户就看到了文字一个接一个跳出来的效果。

### 总结
**SSE 是 AI 时代的“输液管”**。它让巨大的、耗时的 AI 结果能够变成细小的水滴，持续不断地流向用户，消除了漫长等待的焦虑感。
