客户端和服务端建立 Socket（以及初始化上面提到的 TCB 内存空间）的时机，在时间线上是**完全不同步**的。

服务端通常是“未雨绸缪，早早等待”**，而客户端则是**“按需创建，瞬间发起”。

我们可以顺着 TCP 的生命周期，来看它们各自建立 Socket 的精确时机：

## 1. 服务端（Server）：三步走，分为“监听”和“通信”两个阶段

服务端的 Socket 建立过程非常有意思，它其实涉及到 **两种不同角色的 Socket**：

### 阶段一：创建“迎宾（监听）Socket” —— 程序启动时

当你的服务端程序（如 FastAPI、Nginx 或 C++ 写的服务器）刚启动时，就会立刻创建第一个 Socket。

- **时机：** 执行 `socket()` 和 `bind()`、`listen()` 函数时。
- **发生的事情：** 操作系统在内核开辟了一块内存，创建了一个 **监听 Socket（Listening Socket）**。这个 Socket 绑定了服务端的端口（比如 8080），它的唯一任务就是**坐在那里听着，看有没有人来敲门**。此时，三次握手还没有开始。

### 阶段二：创建“专属通信 Socket” —— 三次握手完成时

当有客户端发起连接，三次握手成功后，服务端才会建立真正用于传输数据的 Socket。

- **时机：** 三次握手成功，内核将连接放入队列，应用层调用 `accept()` 返回时。
- **发生的事情：** 操作系统会**复制或全新创建一个“已连接 Socket”（Connected Socket）**。这个新 Socket 才是真正拥有发送、接收缓冲区的“专属驿站”，后续所有的数据读写（`recv`/`send`）都找它。而之前的那个“监听 Socket”则继续回到门口去等下一个新用户。

## 2. 客户端（Client）：一气呵成，瞬间建立

客户端的逻辑就简单直接得多，它不需要“迎宾”，只有在自己想主动找人说话的时候才会创建。

- **时机：** 应用程序准备发起网络请求，调用 `socket()` 以及紧接着调用 `connect()` 的时候。
- **发生的事情：** 1. 当调用 `socket()` 时，操作系统在内核开辟内存，创建客户端 Socket，分配一个临时的随机端口。
  2. 当调用 `connect()` 时，客户端 Socket 立刻向服务端发送 **SYN 包**（正式发起三次握手）。
  3. 当三次握手顺利结束，`connect()` 函数成功返回，这个 Socket 就彻底初始化完毕，进入 `ESTABLISHED` 状态，随时可以发数据。

## 3. 完整的时机对比时序图

为了让你闭着眼睛都能想出这个过程，我们把客户端和服务端放在同一张时间线上：

```
服务端 (Server)                                     客户端 (Client)
   |
   |-- 1. 程序启动，调用 socket(), listen()
   |      【创建了 监听Socket】
   |      状态：LISTEN
   |                                                   |
   |                                                   |-- 2. 想发请求，调用 socket()
   |                                                   |      【创建了 客户端Socket】
   |                                                   |
   |                                                   |-- 3. 调用 connect()
   | <------------------ 发送 SYN ----------------------|      （发起三次握手）
   |
   |-- 4. 收到 SYN，回应 SYN+ACK
   | ------------------ 发送 SYN+ACK -----------------> |
   |                                                   |-- 5. 收到 SYN+ACK，回应 ACK
   | <------------------ 发送 ACK ----------------------|      【客户端 Socket 建立完成】
   |                                                          状态：ESTABLISHED
   |-- 6. 三次握手在内核中完成！
   |      内核自动生成【已连接Socket】
   |      应用层 accept() 成功返回这个新 Socket
   |      状态：ESTABLISHED
   |
```

## 关键避坑总结：数量上的重大区别

- **客户端：** 哪怕要发 100 个并发请求，也需要老老实实创建 100 个不同的客户端 Socket，对应 100 个本地临时端口。
- **服务端：** 无论有 1 万个还是 10 万个客户端连进来，服务端的 **监听 Socket 永远只有 1 个**（守住 8080 端口不放）；但是，内核会为这 1 万个客户端分别创建 1 万个 **已连接 Socket**。

你在写网络通信或者封装网络库的时候，是不是常常需要处理 `accept` 返回的那个新 Socket？对于这两个 Socket 的分工，以前有产生过混淆吗？
